GTFock multi-node scale-out sweep: scheduler records for the Phoenix jobs
========================================================================

Copied verbatim from the run artifacts behind the multi-node tables in
doc/sphinxman/source/gtfock.rst: job 12433686 (peptide), job 12433617
(nanotube) and job 12445512 (protein157 in 6-31G**), plus two jobs that produced
no table row and are kept anyway because the reason each failed is itself a
measurement: job 12433616, a discarded first attempt at the peptide sweep, and
job 12434225, the attempt to run protein157 in 6-31+G** rather than 6-31G**.
Job 12441235 follows 12434225 as its control: a single node running the two
reference J/K arms that 12434225 died before reaching.

These jobs are the companion to the fixed-core jobs recorded in
gtfock_hpc_provenance.txt and ask the opposite question. There, one 24-core node
was subdivided among the ranks; here each rank owns a whole 24-core node, so the
total core count grows 24 -> 48 -> 72 -> 96 with the rank count. Both sweeps ran
the same driver, the same basis, and the same two molecules, so those two sets of
numbers differ only in what was held constant.

Job 12445512 is a later addition and has no fixed-core counterpart. It runs the
same protocol from a separate script, gtfock_hpc_phoenix_protein.slurm, submitted
with FM_BASIS=6-31G**, on a 157-atom fragment pair at 1555 basis functions --
2.7x the nanotube. Two things in that script differ on purpose: a 12-hour
walltime, and 160 GB rather than 120 GB for the single-process reference arms, so
that density fitting at this size keeps its three-index tensor in core instead of
silently falling back to DiskDFJK and comparing a third algorithm under the
second one's name. It did stay in core: the reduced record reports MemDFJK.

For each job, in order: the run's own provenance block; placement.txt, the
hostname-only MPI launch check the batch script runs before any paid SCF (it
FATALs if the ranks do not land on as many distinct hosts as there are ranks);
the sacct query for the job (whose MaxRSS and MaxVMSize columns come back empty
on this cluster, as they did for the fixed-core jobs); and the SLURM epilogue
block PACE appends to the job log after the batch script has already exited.

The epilogue's "Rsrc Used: ... mem=" field is the citable source for job-level
memory: 1653048K (1.58 GiB) for the peptide job, 10801940K (10.30 GiB) for the
nanotube job and 97270096K (92.76 GiB) for the protein157 job. All three are
peaks over the whole job, so the latter two figures are the density-fitting
reference points (10.3 GB and 92.5 GB in one process) rather than any GTFock
point; the GTFock points peak at 3205 MB and 8650 MB summed over four nodes. The
epilogue's "cput" field is allocated core-time, not consumed core-time
(96 cores x the walltime in each of these jobs), so it says nothing about
utilisation. Every per-point number quoted in gtfock.rst comes from
gtfock_hpc_multinode_results.csv instead.

Every node used by these jobs is identical: two-socket Xeon Gold 6226,
CPUTot=24, RealMemory=191000, same feature list. The peptide and nanotube jobs
happened to receive the same four nodes; the protein157 job ran about ten hours
later the same day and drew four different nodes of the same type, checked
identical from the same scontrol query. What matters for the scaling claim is not
that the jobs share hardware but that each job took all of its points from a
single 4-node allocation, so a wider point cannot be faster for having landed on
better hardware.

--- job 12434225, protein157/6-31+G**: FAILED attempt, provenance.txt ---

The reason gtfock.rst reports this molecule in 6-31G** rather than the 6-31+G**
the batch script defaults to. At 1863 basis functions the one-rank GTFock point
ran 101 Fock builds -- the guess plus 100 iterations -- and raised
SCFConvergenceError; under `set -e` that took the rest of the sweep with it, so
after 6h53m on four nodes the job wrote no JSON at all. Both consequences were
fixed afterwards: the script now traps a failing point and continues (the
FAILED_POINTS array in gtfock_hpc_phoenix_protein.slurm), and job 12445512 ran
the same molecule in the smaller basis. The non-convergence itself is a
correctness question still open at the time of writing. No reference arm ever
started here, so job 12441235 below was run to supply them.

--- job 12441235, protein157/6-31+G**: reference arms for 12434225 ---

One node of the same type, same commit, same 24 threads and 160 GB, same molecule
and basis as 12434225. Both reference engines converge in 12 iterations, cleanly
and monotonically, so the non-convergence 12434225 hit is a property of the
GTFock J/K engine and not of the system, the basis or the overlap matrix. Note
that density fitting reports DiskDFJK here rather than MemDFJK: at 1863 basis
functions the packed three-index tensor does not fit even the 160 GB budget, and
the benchmark labels the algorithm it actually got. The 4.35e-03 Eh gap between
the two reference energies is that fitting error, not a defect.

Control point: the one-sided MPI component
==========================================

Both batch scripts export OMPI_MCA_osc=^ucx to silence a per-rank OpenMPI log
line. GTFock's GTMatrix layer does use MPI one-sided RMA (MPI_Win_create,
MPI_Get, MPI_Accumulate, win lock/unlock, in GTMatrix_Get.c and
GTMatrix_Update.c), so across a network that exclusion is an assumption about
which component carries real traffic, not a cosmetic setting. The multi-node
script therefore re-runs its widest point with the variable unset, into
results/<job>/control_osc_default/ so the reducer cannot merge it with the point
it controls. Reduced separately:
